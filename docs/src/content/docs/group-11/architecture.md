# System Architecture

Group 11's Travel Time Estimation (TTE) system is built around three main components, each drawing inspiration from J.R.R. Tolkien's "The Lord of the Rings" universe for their naming.

## Overview

The system provides real-time travel time estimation for routes in road networks by combining machine learning predictions with pathfinding algorithms. Users interact with a web-based map interface to select routes, and the backend processes these requests using historical traffic data and an LSTM neural network to predict travel times.

## Architecture Components

### Frontend - Web Interface

**Location:** `aSTEP-frontend/app/group11`

The frontend provides an interactive map-based user interface built with Next.js and React. Users can:

- **Select Routes**: Click on a map to choose start and end coordinates
- **View Predictions**: Receive travel time estimates and optimal route information
- **Interactive Map**: Visualize routes on an OpenStreetMap-based interface

**Key Features:**

- `RoutePlanner` component for route selection and visualization
- Location picker for coordinate selection
- Route information cards displaying estimated travel times
- Time picker for departure time selection
- API integration with the Elessar backend service

**Technology Stack:**

- Next.js (React framework)
- TypeScript
- Leaflet/OpenStreetMap for mapping
- RESTful API communication

### Telchar - Map Matching Algorithms

**Location:** `telchar` repository

Named after Telchar, the renowned Dwarven smith who forged many legendary weapons in Middle-earth, this component handles the critical task of map matching - aligning GPS trajectory data to the actual road network.

**Purpose:**
Map matching is essential for converting raw GPS traces into accurate road network traversals. This preprocessed data is then used to train the travel time prediction model.

#### Map Matching Implementations

The project supports **two map matching implementations**, providing flexibility in data preprocessing:

**1. Custom Implementation (Telchar)**
Our own map matching solution with the following capabilities:

- **OSM Data Processing**: Extracts and processes OpenStreetMap data to build road network graphs
- **Graph Construction**: Creates vertex and edge representations of the road network
- **Viterbi Algorithm**: Uses the Viterbi algorithm for probabilistic GPS trajectory matching
- **Trip Data Cleaning**: Processes and filters raw trip data
- **Edge Traversal Generation**: Produces edge traversal statistics used for model training

**Technology Stack:**

- Python
- Pandas for data processing
- Custom graph data structures
- Viterbi algorithm implementation

**2. FMM (Fast Map Matching)**
We also utilize the open-source [FMM (Fast Map Matching)](https://github.com/cyang-kth/fmm) library as an alternative map matching solution.

- High-performance C++ implementation
- Supports various map matching algorithms
- Well-established and widely used in research
- Provides additional validation and comparison for our custom implementation

**Data Input Flexibility:**
Both the custom Telchar implementation and FMM can serve as data input sources for the LSTM model training pipeline. This dual-implementation approach allows for:

- Comparison of map matching quality
- Validation of results between different approaches
- Flexibility in choosing the most appropriate solution for different datasets

### Elessar - ML Model & Web API

**Location:** `elessar` repository

Named after Elessar (Aragorn's Quenya name meaning "Elfstone"), this component combines machine learning with high-performance computing to provide the intelligence and API layer of the system.

#### Part 1: PyTorch LSTM Model Training

**Location:** `elessar/pytorch-lstm`

The machine learning pipeline trains a Long Short-Term Memory (LSTM) neural network to predict travel times for road network edges based on temporal patterns.

**Training Process:**

- **Data Input**: Uses edge traversal data generated by Telchar or FMM
- **Model Architecture**: LSTM neural network implemented in PyTorch
- **Hyperparameter Tuning**: Grid search for optimal model parameters
- **Model Export**: Exports trained models to ONNX format for inference
- **Evaluation**: Tracks performance metrics across different time periods

**Key Files:**

- `model.py`: LSTM model definition and training logic
- `gridsearch.py`: Hyperparameter optimization
- `export.py`: ONNX model export functionality
- `data_pred.ipynb`: Jupyter notebook for data exploration and predictions

**Technology Stack:**

- PyTorch for deep learning
- ONNX for model export
- scikit-learn for data preprocessing
- Pandas/NumPy for data manipulation

#### Part 2: Zig Web API

**Location:** `elessar/src`

A high-performance web API written in Zig that serves as the backend for the frontend application, combining pathfinding with machine learning inference.

**Core Functionality:**

- **HTTP Server**: Zap-based HTTP server listening on port 3030
- **Journey Endpoint**: Accepts start/end coordinates and departure times
- **Node Adjustment**: Snaps user-selected coordinates to nearest road network nodes
- **A&ast; Pathfinding**: Implements A* algorithm for optimal route finding
- **LSTM Inference**: Uses ONNX Runtime to run travel time predictions
- **Lookup Tables**: Efficiently retrieves predicted travel times for edges
- **Graph Management**: Loads and manages road network graph data from CSV files

**Request Flow:**

1. Receive journey request with coordinates and departure time
2. Snap coordinates to nearest graph nodes
3. Load graph data (vertices, edges, edge connections)
4. Initialize ONNX Runtime with trained LSTM model
5. Use A* to find optimal path considering predicted travel times
6. Return route and estimated travel time to frontend

**Key Components:**

- `main.zig`: Server initialization and setup
- `web-api/endpoints.zig`: API endpoint handlers
- `astar.zig`: A* pathfinding implementation
- `lstm.zig`: ONNX Runtime integration for model inference
- `lookup_table.zig`: Efficient edge travel time lookups
- Various parsers: Load graph data from CSV files

**Technology Stack:**

- Zig programming language
- Zap HTTP framework
- ONNX Runtime for ML inference
- Custom graph data structures

## Data Flow

```
1. Map Matching (Telchar OR FMM)
   ├─ Raw GPS traces + OSM data
   ├─ Map matching algorithm (Viterbi or FMM)
   └─ Edge traversal data → CSV files

2. Elessar PyTorch (Model Training)
   ├─ Edge traversal data from Telchar/FMM
   ├─ LSTM training
   └─ Trained model → ONNX format

3. Elessar Zig API (Runtime Service)
   ├─ Trained ONNX model
   ├─ Graph data (vertices, edges)
   ├─ HTTP requests from Frontend
   ├─ A* pathfinding + LSTM inference
   └─ Route + travel time predictions

4. Frontend (User Interface)
   ├─ User selects route on map
   ├─ API request to Elessar
   ├─ Display route and travel time
   └─ Interactive visualization
```

## Design Philosophy

The architecture follows a clear separation of concerns:

- **Telchar** focuses on data preprocessing and map matching - the foundation
- **Elessar's ML component** handles model training - the intelligence
- **Elessar's API** provides runtime inference and pathfinding - the engine
- **Frontend** delivers user experience - the interface

The naming convention inspired by Tolkien's works reflects the complementary nature of these components: Telchar forges the foundation (data), while Elessar leads the charge (prediction and routing) to serve the realm (users).
